# Factory glossary

One definition per term. The skills and docs use these words in exactly this sense and point here instead of redefining them.

| Term | Meaning |
|---|---|
| **Job** | One unit of work the factory takes from request to merge: one branch, one PR. Ids look like `J-0003`. |
| **Epic** | A job that is split into slice jobs (several PRs, subsystems or stages); it has its own gates (EH1–EH3). |
| **Recipe** | The ordered list of steps a job runs, chosen by work type and risk (e.g. `bug@low`, `standard@medium`). Recipes live in `recipes/*.json`; the job's copy is frozen in `recipe.lock.json`. |
| **Floor** | A step the policy requires before a milestone (e.g. "review before ship", "CI re-verify after merge"), whatever the recipe says. `factory ship` and the Stop hook refuse while a floor is missing; only the user can waive one. Floors live in `policy/floors.json`. |
| **Outcome contract** | `contract.md` for the job: Intent, Goal, Non-goals, Acceptance criteria (`AC-n`), Constraints, Allowed paths, Verify commands, Assumptions. Everything later is checked against it. |
| **Gate** | A stop where only the user's exact reply moves the job on (`approve` / `deny <what must change>`). H1 contract, H2 design, H3 plan, HF findings, HS ship sign-off, A amendment, EH1–EH3 for epics. An approval is bound to the **hash** of the documents shown; if they change, the gate is shown again. |
| **Park** | The factory stopping instead of guessing: a budget or round cap, no progress, scope drift, a conflict or a failed epic gate. Every park is typed: a **kind** (budget, scope_violation, review_rounds, needs_paths, dependency_conflict, regression, task_exhausted, environment_broken, clarify, manual, …) and a suggested **next** step; `factory why` lists them. Since the 0.10.0 port a loop parks only after it stopped making progress, escalated once to a stronger model and was diagnosed, and the park asks one specific question with options and a recommendation; any reply resumes the job with the user's words (`resume [answer]`), and the budget stays absolute. The user may also reply `cancel job` or `abandon job` (`proceed` only for a clarify cap park recorded by an older factory). |
| **Drive** | `factory drive`: the router loop run by the CLI. It does every step a program can do (CLI steps, briefs, records, ship, distill's bookkeeping, evidence it can check) and returns one typed **stop**: a **hand-off** (a workflow for the main session to run, the lesson writer, evidence to check) or a point where the user is needed (a gate, a clarify turn, a park, a merge, done), which it also notifies. It never answers for the user. See [DRIVE.md](DRIVE.md). |
| **Inbox** | `factory inbox`: everything waiting on the user across jobs, each with the reply and the terminal command. Read-only. |
| **Project brief** | `.factory/project.md`: what every job should know about the repository (conventions, module map, test and lint commands, environment, what ground found, an index of earlier jobs' ADRs and accepted lessons). Every agent brief carries it, trimmed, as data. The user edits it; distill only **proposes** changes (`P1` …), which apply when the user replies `accept brief P1`. |
| **Workflow** | A script in `workflows/` (clarify, ground, fanout-judge, decompose, realize, reconcile) that starts the agents for one step (for clarify, one stage) and returns an envelope. |
| **Brief** | The JSON that `factory wfargs <workflow>` prints for a workflow: which agents to start, their prompts, models and output schemas. Pass it to the workflow unchanged. |
| **Envelope** | The JSON result a workflow returns. Write it unchanged to `.factory/scratch/envelope.json` and run `factory record --file …`; the CLI validates it against `schemas/envelope.json`. |
| **Fan-out** | Several independent agents run in parallel on the same question (options in decide, review lanes in challenge), then a judge merges their results. |
| **Lane** | One reviewer in the challenge fan-out (code, tests, security, UX…). Each confirmed or refuted finding is counted per lane. |
| **Clarify ledger** | Clarify v3's record of items (`I-n`), kept sealed by the CLI in the job's `clarify.json`. Each item has a kind (intent, scope, fact, decision, question, instruction, version pin), a status, a source (the user's words `W-n`, a finding `E-n`, a sheet answer) and a strength: **you** > **evidence** > **accepted** (you took the recommendation) > **assumption**. The user can always reopen an item; an agent overturns one only with stronger evidence, and a conflict with the user's own words goes on the sheet. `factory clarify status` prints it. (Jobs approved under clarify v2 keep their `clarify-ledger.json`.) |
| **Read-back** | Clarify's first screen: what the factory understood (intent, scope), the user's facts quoted, the versions research will use (from a repo file or the user's own words) and the research plan. The user replies ok or says what to change. |
| **Decision sheet** | One screen with at most five decisions (options, evidence, a recommendation) and the facts clarify will assume. One reply answers it, in plain words or structured (`ok, but 2 b`). |
| **Design may choose** | An implementation detail (a library, exact command syntax, parsing) clarify hands to ground and decide instead of asking; it never blocks H1. |
| **Research gap** | Something research could not settle (no source for the confirmed version, the web down, a researcher that came back with nothing). It is listed on the sheet, in the contract's `## Research gaps` and at H1; never hidden. |
| **Redirect** | The user's change of direction (a denial at H1, or `factory clarify redirect`), read back as tracked items and reported done or not done at the next H1. |
| **Relayed words** | The user's words that reached the factory only through the main session (`factory clarify reply`, `clarify redirect`, `job new --request`) and match no message the reply hook saw from them. H1 marks them for the user to check; words the hook saw are the user's own. |
| **God Eye** | The cold critic agent (`factory:god-eye`). It reads the design or plan as if it had never seen the conversation and returns `approve` or `revise`; for a clarify contract it answers a fixed readiness checklist, and a blocker sends the work back to its stage (never a note). |
| **Finding verifier** | An agent that tries to reproduce or disprove one review finding; its verdict decides whether the finding is confirmed or refuted. |
| **Degraded** | A fan-out step finished without one of its angles or lanes (an agent failed twice). The user decides: re-run, or go on without it. In clarify, an agent that returns nothing twice parks the job, naming it. |
| **Decision record** | One line per `factory next` routing decision, with the rule that fired (`factory why` renders them). |
